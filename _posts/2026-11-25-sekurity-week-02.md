데이터 표현과 파일 구조

1. **bit·byte와 진법**

**bit와 byte의 차이**
bit는 컴퓨터에서 데이터를 표현하는 가장 작은 단위, byte는 여러 개의 bit를 묶은 단위

**1byte는 몇 bit인가?**
1 byte = 8 bit

**1byte로 표현할 수 있는 경우의 수**
1과 0  2가지

**2진수, 10진수, 16진수를 사용하는 이유**

컴퓨터의 전자적인 상태를 표현하기 쉽기 떄문에. 컴퓨터 내부에서는 결국 전기 신호를 이용해 데이터를 처리하기 때문에 0과 1을 사용하는 2진수가 적합하다.

**16진수 한 자리는 몇 bit를 나타내는가?**

2진수를 짧게 표현하기 위해 사용한다. 16진수는 한 자리가 4bit를 나타낼 수 있다.

**다음 값을 2진수·10진수·16진수로 각각 표현하기**

**10** 10 1010 A
**65** 65 01000001 41
**255** 255 11111111 FF

**0x41, 0x61, 0x30이 10진수로 각각 얼마인지 알아보기**
65 97 48

2. **signed·unsigned와 endian**

**signed 정수와 unsigned 정수의 차이**

같은 비트 수를 사용하지만, 비트를 해석하는 방법이 다르다.

**1byte 정수의 표현 범위**

**Unsigned** 음수를 표현하지 않고 0 이상의 정수만 표현한다.
**Signed** 양수와 음수를 모두 표현한다.

**같은 비트 11111111이 signed와 unsigned에서 각각 어떤 값인지 알아보기**
signed: -1
-> 00000000 -> 00000001 : 크기가 1인 음수 : -1
unsigned: 255
128 + 64 + 32 + 16 + 8 + 4 + 2 + 1
**음수를 표현할 때 사용하는 2의 보수란 무엇인가?**

2의 보수는 컴퓨터가 음수를 표현하는 대표적인 방법이다.

**big endian과 little endian의 차이**

endian은 여러 byte를 메모리에 저장하는 순서를 의미한다.

**정수 0x12345678을 4byte 메모리에 저장했을 때 byte 순서를 각각 작성하기**

**big endian** 낮은 주소에 큰 자리 byte부터 넣는다 12 34 56 78
**little endian** 낮은 주소에 작은 자리 byte부터 넣는다 78 56 34 12

**endian은 “비트 순서”와 “바이트 순서” 중 무엇에 관한 개념인지 생각해 보기**

endian은 byte의 순서에 관한 개념이다. 여러 바이트로 이루어진 데이터를 메모리에 저장할 때 각 바이트를 어떤 순서를 배치할지를 나타낸다.

3. **ASCII와 UTF-8**

**문자와 byte의 차이**

문자는 사람이 읽고 사용하는 글자를 의미한다. Byte는 컴퓨터가 데이터를 저장하고 처리할 때 사용하는 8bit 크기의 데이터 단위이다.

**문자 인코딩이 필요한 이유**

컴퓨터는 문자를 그대로 이해하는 것이 아니고 0과1로 이루어진 데이터로 저장한다. 그래서 문자를 컴퓨터가 저장할 수 있도록 byte값으로 변환하는 규칙이 문자 인코딩이다. Ex) A-> 41

**ASCII와 UTF-8의 차이**

ASCII는 영어 알파벳 숫자 특수 문자 등을 표현하기 위한 문자 인코딩이다. 기본적으로 7bit를 사용하며 128개의 문자를 표현할 수 있다.
UTF-8은 영어뿐만 아니라 다양한 문자를 표현할 수 있는 인코딩이다. 문자에 따라 사용하는 byte수가 다르다

**UTF-8이 ASCII와 호환된다는 말의 의미**

UTF-8에서는 ASCII에 해당하는 문자들을 동일한 1byte값으로 표현한다. 따라서 영어와 숫자 같은 ASCII문자로 이루어진 기존 데이터를 UTF-8에서도 그대로 사용 가능하다.

**다음 문자가 UTF-8에서 몇 byte인지 확인하기**

**A** 1byte

**1** 1byte

**가** 3byte

😀 4byte

**A, 가, ABC가의 UTF-8 byte를 16진수로 확인하기**

**A** 41
**가** EA B0 80
**ABC** 41 42 43

**한글이 ���� 또는 이상한 문자로 깨져 보이는 이유를 인코딩 관점에서 설명하기**

문자열을 저장할 때 사용한 인코딩과 읽을 때 사용하는 인코딩이 서로 다르면 컴퓨터가 byte를 잘못 해석할 수 있다. 문자 자체가 깨진 것이 아니라 저장된 byte를 올바른 인코딩 방식으로 해석하지 못해서 깨져 보이는 것이다.

4. **Base64와 URL Encoding**

**Base64를 사용하는 이유**

base64는 바이너리 데이터 문자로 표현하기 위해 사용한다. 컴퓨터 시스템에서 이미지,파일 등의 데이터를 텍스트 형태로 안전하게 전달하거나 저장해야 할 때 사용할 수 있다.

**Base64는 암호화인가?**

암호화가 아니라 인코딩이다. 다른 형태로 표현하는 것이기 때문에 누구나 쉽게 원래 테이터로 디코딩할 수 있다.

**Base64 인코딩을 하면 데이터 크기는 대략 어떻게 변하는가?**

base64를 인코딩하면 원래 데이터보다 33% 정도 크기가 증가한다. 3byte의 데이터를 4개의 base64 문자로 표현하기 떄문.

**URL Encoding이 필요한 이유**

URL에는 특별한 의미를 가지는 문자들이 있다. ex) ? & = # %
한글처럼 URL에서 직접 안전하게 표현하기 어려운 문자도 있다. 그래서 URL에서 사용할 데이터를 안전한 형태로 변환하기 위해 URL Encoding을 사용한다.

**%EA%B0%80가 어떤 문자이고, 각 숫자가 무엇을 의미하는지 알아보기**

UTF-8로 인코딩된 가 를 URL Encoding한 것이다.
가 -UTF-8>  EA  B0  80
URL Encoding: %EA %B0 %80
%EA EA라는 1byte
%B0 B0이라는 1byte
%80 80이라는 1byte

**공백이 URL에서 %20 또는 +로 표현되는 경우의 차이 알아보기**
[;l'[o;.]]
%20 공백의 byte값을 URL Encoding한 표현이다.
+는 쿼리 문자열이나 폼 데이터에서 공백을 간단하게 표현하는 방식이다.

**Base64와 URL Encoding의 공통점과 차이점 정리하기**

Base64는 바이너리 데이터를 텍스트로 표현하기 위한 인코딩이고
URL Encoding은 URL에서 특수 문자나 데이터를 안전하게 표현하기 위한 인코딩이다.
둘다 모두 암호화가 아닌 인코딩 방식이다.

5. **파일의 magic과 header**

**파일 확장자와 실제 파일 형식의 차이**

파일 확장자는 파일 이름 뒤에 붙어 파일 종류를 나타내는 표시이다. 실제 파일 형식은 파일 내부의 데이터 구조와 규칙을 의미한다.

**파일 magic number 또는 file signature란 무엇인가?**

파일의 시작 부분에 있는 특정 byte값으로 파일 형식을 식별하는데 사용된다. 확장자가 변경되어도 파일 내부의 signature는 그대로 남아있다.

**파일 header에는 어떤 정보가 들어갈 수 있는가?**

파일 형식, 파일 크기, 버전, 이미지 크기, 압축 방식 등 파일을 해석하는 데 필요한 정보가 들어갈 수 있다. 파일 형식에 따라 저장되는 정보는 다르다.

**다음 파일 형식의 대표적인 시작 byte를 조사하기**

**PNG** 대표적인 시작 byte는 89 50 4E 47 0D 1A 0A이다.
**JPEG** 대표적인 시작byte는 FF D8 이다
**PDF** 대표적인 시작byte는 25 50 44 46이다
**ZIP** 대표적인 시작byte는 50 4B 03 04이다 

**PNG 파일의 확장자를 .txt로 변경하면 실제 파일 형식도 바뀌는지 생각해 보기**

확장자만 .txt로 변경해도 파일 내부의 PNG 데이터는 그대로 이므로 실제 형식은 PNG이다. 파일 형식을 바꾸려면 데이터를 해당 형식에 맞게 변환해야 한다.

**Linux의 file 명령은 파일 형식을 어떻게 추측하는지 알아보기**

file명령은 단순히 파일 확장자만 확인해서 판단하지 않는다. 파일의 내용, 특히 파일의 시작 부분에 있는 Magic Number/File Signature와 파일 구조 등을 확인하고 알려진 파일 형식의 특징과 비교하여 파일 종류를 판단한다.

5. 생각해 볼 문제
- 파일 확장자만 보고 파일 형식을 판단하면 위험한 이유는 무엇인가?
확장자는 파일 이름의 일부일 뿐 실제 파일의 내부 형식을 보장하지 않는다. 예를 들어 PNG 파일의 확장자를 .txt 로 변경해도 파일 내부의 PNG 데이터는 그대로이기 때문에 확장자만으로 파일 형식을 판단하면 잘못 판단할 수 있다.

- Base64로 인코딩한 비밀번호가 안전하지 않은 이유는 무엇인가?
Base64는 암호화가 아니라 데이터를 다른 형태의 문자열로 표현하는 인코딩 방식이다. 따라서 Base64로 인코딩한 비밀번호는 누구나 쉽게 원래 문자열로 디코딩할 수 있으므로 비밀번호를 보호하는 방법으로 사용할 수 없다.
